# Author revenue agreements

`GET /api/admin/authors/:accountId/agreement` requires Admin authorization, validates the account ID and returns private/no-store data. Only an actual account with `everAuthor: true` can be inspected, including former Authors. Missing, non-Author and anonymized accounts return 404 without substituting a demo account.

The current percentage is the latest personal AuthorRevenueRate whose effectiveAt is no later than the server time. Otherwise it uses the latest effective PolicyVersion whose effectiveAt has arrived; without either record, the confirmed product default is 70/30. Future rates and policies do not override today's percentage. The response includes at most 20 newest personal rate records, explicitly marking future effective dates, plus the account version and latest appended rate ID used to guard writes. No actor email, private account fields or monetary balances are exposed.

`POST /api/admin/authors/:accountId/agreement` requires a JSON integer `percentage` from 0 through 100, a trimmed reason of 1–1000 characters, `expectedAccountVersion`, and nullable `expectedLatestRateId`. Unknown fields, client-provided effective dates and invalid IDs are rejected. A new rate takes effect at server time; backdating, future scheduling, updating and deleting past records are not exposed by this command. Existing future-dated rates remain in force at their own effective time; the form explicitly explains this. Personal rates override platform defaults.

The transaction checks the Admin's current account state, authorization epoch, credential version and active Admin assignment, then locks the target account with its expected version. The target must remain active or suspended and retain an active Author assignment. Former Authors can inspect history but cannot receive a new agreement here. A stale latest rate ID is rejected even if an out-of-band insert did not increment the account version. Account locks serialize these writes with Author revocation and other supported account commands. Concurrent or repeated submissions with the same prepared version create at most one rate; stale commands return 409. Each successful append and its mandatory reason/digest audit event commit together; audit failure rolls back both account versions and the rate. No backend schemas/models changed.

The existing Admin route uses the actual identity, split and bounded history with loading, missing, error and retry states. The original two-column split geometry, progress bar, Card/Input/Button primitives and Admin shell remain. Eligible Authors have an editable percentage and required reason; platform share is derived. Save/discard controls appear only with edits. Invalid percentages and blank reasons cannot submit. The form prevents duplicate requests and waits for a response matching the exact author and percentage before showing success, then reloads actual MongoDB data. Any failed or uncertain save requires a fresh GET before another write, including a lost response that might follow a committed transaction. Inputs remain visible on failure. Active Authors have an inspector link from the user directory. This page no longer uses localStorage mock saving or the 80% sample fallback; other MockDataContext consumers are unchanged.

Existing wallets, revenue allocations, payout records and old rates are untouched. Recording an agreement is not an implementation of unlock settlement or payout execution. Tests and browser proof use disposable MongoDB fixtures and never seed or alter shared account/financial data.

Validation covers Admin access, strict input validation, account isolation, effective-time precedence, 70/30 defaults, stale/latest-rate guards, simultaneous submissions, replay, audit rollback, role revocation, 0/100 bounds, retained future rates and immutable allocation snapshots. Frontend tests cover actual API data, save/reload, validation/discard, duplicate clicks, stale data and malformed responses. Browser verification saved 78/22, reloaded actual data and confirmed two rate records (future 85% plus current 78%) with exactly one audit. Light/dark checks at 390/768/1024/1536px showed no horizontal page overflow; keyboard Tab reached the reason input and browser error logs were empty.

Validated transaction milestone: 11 MongoDB tests and 10 related frontend tests passed; lint, i18n (1,521 keys), icon checks and production build passed. Browser save/reload proof uses an isolated temporary database, not the shared environment.

## Author earnings view

`GET /api/author/earnings` also returns an allowlisted `agreement` object for the authenticated Author only: current author/platform percentages, source and effectiveAt. Both Admin and Author views share `currentAuthorAgreement`, including the same effective-time and policy/default precedence. Admin account-version/latest-rate write tokens and other Authors' agreements are not exposed. The endpoint uses private/no-store caching; owner IDs in the query are rejected by its strict schema.

The earnings sidebar displays these actual current terms in the existing Card style and supports reloading the server data. Loading/error states do not fall back to 70% or 80% in the browser. Zero percent is valid. Existing historical credits and wallet balances continue to come from their original ledger and wallet sources; the current split does not recalculate those records. The aggregate `creatorShare` remains unavailable rather than misrepresenting current terms as a historical effective rate. No Author write controls are added.

Author view validation: 13 related MongoDB tests and 10 related frontend tests passed. Browser proof shows current 79/21 after the real Admin command while the future 90% rate is not applied; 100 recorded ledger coins and a 555-coin wallet remain unchanged after reload. Light/dark 390/768/1024/1536px checks showed no horizontal page overflow and browser error logs were empty. All figures came from isolated MongoDB fixtures; the helper/database were stopped afterward.
