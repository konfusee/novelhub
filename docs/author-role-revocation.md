# Author role revocation and unreleased publication

Admin preparation: `GET /api/admin/authors/:accountId/role`, private and not cached, returns the target account/version and exact active Author assignment/version. `POST /api/admin/authors/:accountId/revoke` accepts only `roleId`, `expectedRoleVersion`, `expectedAccountVersion`, and a non-empty `reason` (maximum 1,000 characters). Both routes require an authenticated Admin. The mutation rechecks the Admin account epoch, credentials and active Admin assignment inside the transaction.

Revocation locks the target account using its prepared version, increments its authorization epoch, revokes the exact role assignment and records its revocation time. All owning stories become frozen; published stories retain publication state, snapshots and release dates. Draft/submitted/approved/scheduled/due/archived chapters become `cancelled` with `author-role-removed`. Already deleted draft tombstones remain unchanged. Published and unpublished chapters retain their existing state, bindings, release dates and access policy. Immutable content, media, entitlements, wallet and finance records are untouched.

Unreleased validated/pending/decision-pending/approved submissions become cancelled, excluding revisions still bound as published story/chapter snapshots. Claims are released with the previous owner/version/expiry retained in claim-release history and a bumped claim version. Each cancellation records audit and moderation history; the completed role action includes the Admin reason and affected counts. Nothing is hard deleted. These statuses remove pending work from a status-filtered moderation queue; the future similarity pipeline must continue excluding cancelled work.

The role mutation, account epoch, story freeze, chapter/submission changes and audit/history writes commit together. Audit or moderation-history failure rolls everything back. Duplicate/stale requests return 409 and require a fresh preparation. Account locking serializes the operation with publishing: an already committed publication remains live and frozen; a revocation committed first prevents release. A later Author grant does not restore cancelled chapters or unfreeze stories.

Suspension is different: the existing release guard leaves a chapter due while the account is suspended and can release it after reinstatement. It does not turn suspension into permanent cancellation.

Scope: backend revocation API and publication lifecycle only; no schema/model changes and no frontend modifications. An Admin confirmation UI, account suspension/deletion management, finance closure and deletion-specific `account-deleted` cancellation remain separate work. Direct database edits bypass this transactional lifecycle and are not a supported revocation workflow.

Tests use isolated disposable MongoDB and explicit approval fixtures. Coverage includes future schedules and claimed submissions, unchanged live content, frozen authoring, invalidation of old sessions, exact role/account versions, authorization and reason validation, duplicate/concurrent operations, revocation racing release, regrant without resurrection, suspension/reinstatement, deleted tombstones, and audit/history rollback. See `backend/test/author-role-revocation.test.js`; chapter release regression remains in `backend/test/author-chapter-release.test.js`.

Validation: all 71 related backend tests passed (10 revocation, 49 chapter release and 12 Author access/application tests), along with backend lint and targeted formatting. Frontend and API readiness both returned HTTP 200. The existing frontend was not modified by this increment.
