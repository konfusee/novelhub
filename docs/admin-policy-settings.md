# Admin publishing policy settings

`GET /api/admin/policy` requires an active authenticated Admin and returns a private, non-cacheable view of the latest `effective` PolicyVersion whose effectiveAt is not in the future. Ordering is effectiveAt descending, then _id descending, matching Author early-access configuration. The DTO exposes identity/version, effective date, price/duration bounds and default revenue shares. No policy returns `{ policy: null }`; no example defaults are substituted.

`POST /api/admin/policy` creates and immediately activates a new policy. Its strict input requires integer minimum/maximum coin prices, positive integer minimum/maximum days, a reason, and nullable expectedPolicyId/expectedPolicyVersion. Minimum cannot exceed maximum. Clients cannot backdate or override other policy fields through this endpoint.

Inside one MongoDB transaction, the service locks/rechecks the active Admin account and role, verifies the exact current policy/version, supersedes that record, creates a new effective record, and writes `policy.activated` audit evidence. Existing bounds on the old policy remain unchanged. Author policy pinning also increments the policy version, so an Admin view predating an Author configuration requires reload. Audit failure rolls back every write. First initialization uses reserved policy identity `000000000000000000000001`; the existing unique _id index serializes concurrent initialization by different Admins without a lock collection or schema change. A duplicate first-initialization identity returns 409. Subsequent activations serialize against the previous policy version. All supported policy writes go through this endpoint.

The new policy inherits withdrawal threshold, revenue shares, order expiry and claim expiry from the previous policy. First initialization uses the existing schema defaults (70/30 shares, 100,000-coin withdrawal threshold and 24-hour order/claim expiry), disclosed in the form. Those fields are not editable in this milestone. Existing chapter policy references, configured prices/durations and financial allocations are untouched. Existing future-effective policies block immediate activation with 409, preventing a newly entered policy from being unexpectedly replaced by an already scheduled record. Managing scheduled policy records remains outside this command.

The existing `/admin/settings` shell loads actual policy data and offers initialization/replacement using shared form primitives. It requires changed bounds and a reason, blocks duplicate submits and reload during a write, verifies a new returned policy identity, and reloads actual server state after acceptance. Failed or uncertain writes require reload before retry. Loading, empty and error/retry states are explicit. Author-specific revenue agreements retain precedence over default policy shares. Other service/audit tabs remain mock and are identified as such.

Validation: 12 backend policy tests plus 17 existing Author early-access tests pass. They cover role boundaries, strict validation, effective-policy selection, initialization/replacement, multi-Admin races, stale tokens, Author pin invalidation, future-policy blocking and transaction rollback including first initialization. Eight frontend tests cover actual request fields, validation, duplicate prevention, response validation, empty storage and reload/error handling. Root lint, Vietnamese content checks and production build pass. Browser tests use a disposable MongoDB replica set and real APIs: initialize at 300 coins, replace with 350, then verify one superseded record with unchanged bounds, one effective record and two audit entries. Main/shared database data is not modified. Light/dark responsive proof images are outside the repository at `WDP301/outputs/author-progress-01a13e25/policy-activation`. Development HMR after changing both locale and form required a cold reload; the cold page and persisted database state were then rechecked.
