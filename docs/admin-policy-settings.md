# Admin publishing policy settings

`GET /api/admin/policy` requires an active authenticated Admin and returns a private, non-cacheable view of the latest `effective` PolicyVersion whose effectiveAt is not in the future. Ordering is effectiveAt descending, then _id descending, matching Author early-access configuration. The DTO exposes identity/version, effective date, price/duration bounds and default revenue shares. No policy returns `{ policy: null }`; no example defaults are substituted.

`POST /api/admin/policy` creates a new policy, immediately by default or at an optional future effectiveAt. Its strict input requires integer minimum/maximum coin prices, positive integer minimum/maximum days, a reason, and nullable expectedPolicyId/expectedPolicyVersion. Minimum cannot exceed maximum. Optional authorSharePercent (integer 0–100) and withdrawalThresholdCoins (nonnegative safe integer) can be changed in the same activation. The server computes platformSharePercent as 100 minus authorSharePercent. Omitted finance fields inherit the previous policy, preserving compatibility with bound-only callers. Clients cannot backdate or send a platform share. Expiry fields are configurable as described in the later milestone.

Inside one MongoDB transaction, the service locks/rechecks the active Admin account and role, verifies the exact current policy/version, supersedes that record, creates a new effective record, and writes `policy.activated` audit evidence. Existing bounds on the old policy remain unchanged. Author policy pinning also increments the policy version, so an Admin view predating an Author configuration requires reload. Audit failure rolls back every write. First initialization uses reserved policy identity `000000000000000000000001`; the existing unique _id index serializes concurrent initialization by different Admins without a lock collection or schema change. A duplicate first-initialization identity returns 409. Subsequent activations serialize against the previous policy version. All supported policy writes go through this endpoint.

The new policy inherits withdrawal threshold, revenue shares, order expiry and claim expiry from the previous policy. First initialization uses the existing schema defaults (70/30 shares, 100,000-coin withdrawal threshold and 24-hour order/claim expiry), disclosed in the form. Author share and withdrawal threshold are editable; the expiry milestone below adds optional order/claim expiry fields. Existing chapter policy references, configured prices/durations and financial allocations are untouched. Existing future-effective policies block immediate activation with 409, preventing a newly entered policy from being unexpectedly replaced by an already scheduled record. The scheduling milestone below adds creation of one future version through the same command.

The existing `/admin/settings` shell loads actual policy data and offers initialization/replacement using shared form primitives. It requires changed bounds and a reason, blocks duplicate submits and reload during a write, verifies a new returned policy identity, and reloads actual server state after acceptance. Failed or uncertain writes require reload before retry. Loading, empty and error/retry states are explicit. Author-specific revenue agreements retain precedence over default policy shares. Other service/audit tabs remain mock and are identified as such.

## Default revenue and withdrawal-threshold milestone

Admin can change only finance terms while keeping price/duration bounds unchanged. The read DTO also displays the stored withdrawal threshold and order/claim expiries. Defaults are visible only as explicit initial form proposals when no effective policy exists. Author-specific agreements continue to take precedence. No historical allocation, wallet, ledger or payout record is rewritten; automatic withdrawal evaluation/payment is not implemented by these settings.

## Policy history milestone

`GET /api/admin/policy/history?page=1&pageSize=5` is Admin-only, private/no-store and strictly validates bounded pagination (page 1–100,000, pageSize 1–20). It returns policy snapshots sorted by effectiveAt and _id descending, a stable current-policy identity, future/draft/superseded state, pagination totals and an optional accepted activation reason. A read-only snapshot transaction keeps the page, count and current identity consistent while activation runs concurrently. No policy/account/audit record is changed. The DTO excludes actor identifiers, account information and audit digests. Records without an activation audit show no invented reason; missing effective dates stay null. No historical policy is relabeled merely because a future version exists.

The existing settings panel now includes a paginated history section using real API responses. It displays exact policy IDs, relevant saved bounds, revenue shares, withdrawal thresholds, status and recorded reason. Loading, empty, error/retry and out-of-range empty pages are explicit. History reload/pagination does not reset an unsaved settings form. Successful activation reloads current data and remounts history at page one so the new version and recorded reason are visible. Other service/audit mock tabs are outside this feature.

Validation: 18 backend policy tests and 15 frontend settings/history tests pass; lint, Vietnamese content validation, production build and target formatting pass. Browser verification uses a disposable MongoDB replica set: seven existing records paginate across two pages; an unsaved 400-coin edit survives history navigation; saving produces eight policy records and one accepted activation audit, then history returns to page one with the exact stored reason. ## Cancel a future policy schedule

`POST /api/admin/policy/:policyId/cancel` accepts an exact expectedVersion and a required trimmed reason. It requires an active current Admin both at the HTTP boundary and inside the transaction. Only a record with status effective and effectiveAt strictly later than server time can be cancelled; missing IDs return 404, stale/current/past/draft/superseded records return 409, malformed or unknown fields return 400. The command locks/rechecks the actor, compares the target policy version, changes only status to superseded and increments its version, then appends `policy.cancelled` audit evidence in the same transaction. Audit failure rolls back both actor and policy changes. Concurrent cancellation and replays cannot create duplicate audit records.

Cancellation retains the policy terms, effective date and original activation evidence. History now joins accepted activation and cancellation reasons separately and marks cancelled schedules explicitly. The current effective policy and existing chapter/finance data remain unchanged. Once no future effective records remain, the existing immediate-activation command can proceed normally. The scheduling milestone below adds creation of future policy records. The later milestones add stored expiry configuration and one-step rescheduling.

History offers the action only for server-marked future records. A shared Modal identifies the exact policy and requires a reason/confirmation. It blocks duplicate submissions and closing while saving; an uncertain or stale result requires closing and reloading history before retry. Successful cancellation closes the dialog and refreshes history without resetting unsaved settings in the parent form.

## Schedule a future policy version

The same POST command accepts an optional ISO effectiveAt with an explicit UTC offset. It must be strictly after server time. Initialization remains immediate only: a current policy is required before scheduling. Only one future effective record may exist; cancel it before creating a replacement or activating immediately. Scheduling unchanged terms is allowed.

The transaction pins/increments the exact current policy version without superseding it, creates the future record, and records policy.scheduled with the supplied reason. The old terms remain applicable until the scheduled instant. Existing date-based selectors choose the new version at that boundary without a worker. Historical records retain their stored status; the history DTO derives which version is current. A scheduled response includes the normalized effectiveAt. Audit failure rolls back all writes, including the actor/current-version pins. Concurrent scheduling and immediate activation cannot both succeed against the same current version. No schema, chapter terms, existing financial allocation or shared application data is changed.

The existing form offers an optional local date/time with an explicit browser-timezone hint, converts it to UTC for transport, and checks the clock again on submit. Missing/past times cannot submit. Response identity/version and exact effective time are verified before showing success. History displays date and time, the scheduling reason and the existing cancellation action. Current policy data stays unchanged after scheduling, apart from its concurrency version.

## Versioned order and claim expiry configuration

POST /api/admin/policy now accepts optional orderExpiryHours and claimExpiryHours as nonnegative safe integers, matching the existing model's minimum without changing its schema. Omitted values inherit the previous policy; first initialization retains schema defaults. Explicit values apply to the newly created policy only, including scheduled versions. They use the same authorization, expected identity/version, transaction and audit guarantees as other policy terms.

The existing settings form exposes both durations, proposes 24 hours only for initial creation, and allows expiry-only changes with a reason. It rejects empty, fractional, negative and unsafe values. The policy history now displays the two stored durations as well as the current-policy panel. A common saving label accurately covers both immediate activation and future scheduling.

This settings command stores and exposes policy configuration. Existing TopUpOrder.expiresAt, PublicationSubmission.claimExpiresAt, leases, financial records and previous policy terms are never recalculated by this command. Zero is an explicit stored duration permitted by the existing schema, not an invented unlimited-duration flag.

## Policy-bound top-up invoices (18 October 2026)

`POST /api/reader/top-up-orders` accepts only an active fixed package ID. It creates a pending MongoDB invoice with a cryptographically random unique `NH` + eight-digit code, a package/current effective policy snapshot, and `expiresAt` computed from that policy's `orderExpiryHours`. Future policies are ignored until effective. Missing, zero or invalid expiry blocks new invoices rather than inventing an unlimited deadline. Policy/package edits never recalculate an existing invoice.

Account-serialized duplicate requests reuse the same unexpired invoice for that package. Creation normalizes that owner's expired pending invoices; owner-only GET reports expiry even before the next creation. Audit failure rolls back invoice/wallet creation. Four isolated MongoDB tests verify snapshots, concurrency/reuse, expiry/new terms, access guards and rollback. No wallet credit or ledger credit occurs at invoice creation.

This endpoint is not yet wired into the existing wallet payment UI. Bank transfer instructions/VietQR, SePay receipt matching, moderator claim acquisition and financial settlement remain separate unfinished flows. A-UC-05 is still partial; no payment completion is inferred from a pending invoice.

Verification: all 35 backend policy tests and 26 frontend settings/history/cancellation tests pass in focused runs. UI tests cover initial proposals, expiry-only requests, validation and history values. Root lint, Vietnamese content checks and production build pass. Full frontend-suite success is not claimed. ## Atomic schedule replacement

POST /api/admin/policy/:policyId/reschedule accepts the exact expectedVersion, a required reason and a different future effectiveAt with explicit UTC offset. Only an active Admin may call it, with account/role rechecked inside the transaction. Missing targets return 404; stale, current, past, draft, cancelled or ambiguous multiple-future schedules return 409. A current effective policy must exist. Time input is validated against server time; an equivalent instant using another offset is still unchanged and rejected.

In one transaction, the command cancels the exact future version and creates a new policy identity with all nine price/duration/revenue/threshold/expiry terms copied unchanged. It writes policy.cancelled for the old identity and policy.scheduled for the replacement, using ordered inserts within the session. The old date, terms and original scheduling reason remain available in history alongside the new cancellation reason. The current effective policy is not modified or pinned; its existing form tokens remain valid. A failure, including either audit write, rolls back the replacement, cancellation and actor pin. Concurrent replacement/cancellation cannot both succeed against the same version. No schema or chapter/financial data changes are required.

History exposes a shared Modal only for future records. It shows the exact policy identity and old schedule, requires a new local date/time and reason, explains the browser timezone, and rechecks the clock on submit. Duplicate submits and closing while saving are blocked. Success requires matching old identity/incremented version, a distinct valid new identity/version and the exact requested UTC time. Uncertain responses retain entered data and require closing/reloading. Accepted replacement refreshes history on page one without remounting or resetting the parent's unsaved settings form.
