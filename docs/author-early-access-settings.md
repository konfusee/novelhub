# Chapter early-access settings before first release

Authors can open “Thiết lập đọc sớm” from eligible chapter rows in the story manager. The existing shell, table, shared Modal/Input/Button components and semantic colors remain. The manager shows a saved draft price/duration separately from its unreleased status; no paid publication is implied.

`GET` and `PUT /api/author/stories/:storyId/chapters/:chapterId/early-access` require the current Author account and ownership. Read responses are private/no-store. Setting a price or duration requires an editable draft revision belonging to that exact story/chapter/Author. As a separate one-way operation, an approved, scheduled or due chapter may have its existing early-access settings disabled before its first release, provided the owned revision is approved and immutable. Its price and duration cannot be edited or enabled at those stages. Submitted, published, archived, cancelled or previously released chapters remain blocked; frozen/reviewing/archived stories are also blocked. Original first-release dates and early-access end dates are never reset by this command.

Enabling requires safe integer price/duration values within an actual, effective MongoDB PolicyVersion. There is no invented frontend policy or silent policy fallback. Default product policy values are 200–5,000 coins and 1–14 days when an Admin has installed that policy. Future or draft policy records are not selected. The request carries chapter/story versions and the exact policy ID/version. The transaction locks the Author account, checks current authorization, pins the policy version, updates chapter settings and increments the story version, then appends the required audit event with before/after settings, policy facts and a digest. Failure rolls back all writes. Stale or duplicate concurrent writes cannot overwrite newer settings. Disabling clears unreleased settings and remains possible without an effective policy. It preserves the approved revision, chapter state, requestedReleaseAt and all publication/access history. A scheduled chapter still waits for its original time and every existing release guard.

This is preparation for early access, not the paid-release/unlock/settlement workflow. It never sets endsAt, firstReleasedAt, publishedRevisionId, a public status or any financial record. The existing release guard continues to reject enabled early-access chapters; the form states that the present publication flow is free-only and the setting must be disabled before using that flow. First paid publication, immutable release-time terms, entitlement purchases, settlement and automatic expiry integration still remain. No backend models/schemas changed.

The form loads fresh settings/policy, validates integers and bounds, avoids duplicate pending requests and requires a reload after failed or uncertain writes. It only closes as successful after a matching chapter/settings/version response. Missing policy, locked chapter, load errors and write errors have explicit states. Frontend tests remain under frontend/test.

Validation: 12 dedicated MongoDB tests plus 49 chapter-release regressions passed. Seven dialog tests and 16 story-manager tests passed. Lint, i18n (1,546 keys), icon checks and production build passed. Browser proof on a disposable MongoDB instance performed enable 350/5, reload, change to 400/7, reload and disable. Final database evidence: settings null, chapter still draft, no firstReleasedAt and exactly three audit records. Light/dark checks at 390/768/1024/1536px showed no horizontal page overflow; the browser error log was empty. No fixtures were inserted into the shared database.


## Approved-to-free correction

The original draft-only UI could strand an enabled chapter after approval because the current release service accepts free chapters only. The API now reports separate canEdit and canDisable capabilities. The manager opens the existing form for eligible approved/scheduled/due chapters; only its checkbox can change. The save handler and server both reject enabling or repricing in this mode, including forged events and requests. Clearing the settings is explicit, version-checked and audited; it does not publish, cancel the schedule, reopen the revision or bypass review/order/parent guards.

Follow-up tests cover all three states, immutable-content preservation, blocked re-enable/reprice, already-released protection, rollback when the disable audit fails and an integration test that clears settings and then publishes through the full existing free-release path. Browser proof uses an isolated scheduled fixture: after clearing, settings are null, status remains scheduled, requestedReleaseAt remains 2030-01-01, firstReleasedAt is absent, the approved revision digest is unchanged and exactly one audit exists. Four viewport widths in light/dark showed no page overflow. A temporary dev hot update of locale/page required a reload; the fresh page then completed the save and final browser error logs were empty. This is not a paid publication or unlock implementation.

Follow-up validation: 17 dedicated settings tests and 50 release regressions passed; nine dialog and 16 manager tests passed. Lint, i18n (1,548 keys), targeted formatting and production build passed. The shared backend/frontend were left running; disposable fixtures were not written to the shared database.
