# Scout report: backend moderation review & AI-evidence surface (NovelHub)

Paths are relative to `novelhub/backend/` unless stated. Line numbers come from direct reads/greps; ranges marked `~` are approximate (±3 lines) because the read tool elided some bodies. No repo file other than this report was written; no tests/DB/OpenAI calls were run.

## Summary (what the planner must know)

1. **Nothing processes submissions today.** `submitContent` writes `PublicationSubmission{status:'validated'}` + `EvidenceBatch{stage:'embedding',status:'pending'}` and stops (`src/modules/author-submissions.js:336-364`). No code anywhere moves a submission to `pending-review`/`decision-pending`/`approved`/`rejected`; tests fake approval by direct `save()` (§7).
2. **No `forwardOnly` guard exists on Story, Chapter, ContentRevision, PublicationSubmission, EvidenceBatch.** Every transition you listed is NOT blocked at the model layer (§3). `forwardOnly` is only on RightsDeclaration, ProcessingAttempt, DeliveryAttempt, UnlockEntitlement/Request, WithdrawalRequest (`src/models/**`; grep result in §3). Real blockers are: `lockFields` on ContentRevision content fields (frozen by `immutableAt`), `Chapter.firstReleasedAt` set-once, `appendOnly` on ModerationHistory/AuditEvent/SimilarityFinding/EmbeddingArtifact, and `mutableOptions` optimistic concurrency (`version`) + `strict:'throw'`.
3. **Release gates define exactly what "approved" must look like** (§4): submission `approved`, revision `approved|immutable` with `immutableAt`, story `publicationStatus` in `approved|published|unpublished` AND `authoringFrozen=false` (story), chapter `status` `approved|published` AND parent story `authoringFrozen=false`, evidence batch terminal (`available-for-human-review`+`stage:'llm'` OR `failed`+`failedStage`). So **story approval must also clear `authoringFrozen`** (the test fixtures do: `author-story-release.test.js:55-61`), even though the settled decision text only mentions clearing it on rejection.
4. **`reviseSubmission` already handles `rejected`** and itself unfreezes the story (`author-submissions.js:580-586`). With "rejection unlocks immediately" the decision transaction does the unlock and `reviseSubmission` must tolerate an already-unfrozen story / already-draft target (idempotent) — it currently keys only on `submission.status==='rejected'` (`:529`) and, for chapters, *throws* if `story.authoringFrozen` (`:513-514`).
5. **Notification pipeline is half-built:** `Notification`, `NotificationOutbox`, `DeliveryAttempt` models exist, but only `decideApplication` creates a `Notification` row; no outbox writer, no outbox worker, no email template for decisions. `reader-data.routes.js` already recognises event type `publication.decided` (→ `/author/submissions`).
6. **Background jobs:** only `startChapterScheduler` (setInterval 30 s, `.unref()`, no-overlap flag, returns async stop fn) wired in `server.js`. Tests call the exported sweep function directly, never the timer. Template to copy for an AI evidence worker.
7. **Test DB has no mongot** → any `$vectorSearch` stage must be behind an injectable provider/port; global-setup is `MongoMemoryReplSet` 8.3.13 (`test/global-setup.js:1-15`), `mongodb-memory-server ^11.3.0` (`package.json` devDeps).

| Transition | Blocked by a guard? | Evidence |
|---|---|---|
| Chapter `submitted→draft` | **No** (no forwardOnly on Chapter) | `chapter.model.js:55` is the only guard (firstReleasedAt). Already done today by `reviseSubmission` `author-submissions.js:581`. |
| Chapter `published→unpublished`/`unpublished→draft` | No | same |

| Story `authoringFrozen true→false` | No | no guard; done at `:583`. |
| Revision `submitted→rejected` / `→approved` | **No** | content-revision `lockFields` excludes `status`; `status` has no forwardOnly. |
| Submission `validated→pending-review→decision-pending→approved/rejected` | **No** | no guards on PublicationSubmission; tests set `approved` via plain `save()`. |

## Concrete implications for the plan (derived, not decided)

1. New moderator module(s) should live in `src/modules/` (the `modules/moderation/` and `modules/ai/` dirs exist but are empty `.gitkeep`; all current modules are flat files in `src/modules/` and routes in `src/routes/` — follow the flat convention or deliberately use the empty dirs).
2. Decision tx order (mirrors `decideApplication` + `submitContent`): `withTransaction` → `lockAccount(moderator)` + moderator RoleAssignment check → load submission → CAS `{status ∈ [pending-review, decision-pending], version===expectedVersion}`, not `cancelled`, `currentEvidenceBatchId` terminal (or manual-fallback) → lock author `Account` (CAS on `authorizationEpoch`) → update revision (`submitted→approved|rejected`), submission (`approved|rejected`, `decisionSummary`, clear claim + push `claimReleaseHistory`, `claimVersion++`), target (approve: story `publicationStatus='approved'` unless `published`, `authoringFrozen=false` (needed for release gate), chapter `approved` unless `published`; reject: same mapping as `reviseSubmission:581-585`, but only clear freeze when not set by role-removal/account-deletion) → `ModerationHistory{action:'decided'|…, outcome, feedback, reason, submissionId, revisionId, evidenceBatchId, evidenceBatchVersion, actorAuthorizationEpoch, before/afterStateDigest, correlationId}` + `AuditEvent` + `Notification{eventType:'publication.decided', sourceEventKey:`submission:${id}:decision`}` (+ optional outbox row `channel:'email'`).
3. Reject requires non-empty feedback (zod `.trim().min(1).max(...)` like `decisionSchema`); approve may omit.
4. AI worker: copy `startChapterScheduler` shape (interval, `running` guard, `unref`, stop fn, exported `sweep(config,{now})` for tests), wire in `server.js:37` & `shutdown`; claims via `ProcessingAttempt` (`attemptKey` unique ⇒ deterministic keys; `leaseId/leaseExpiresAt/claimVersion`), stage CAS via `EvidenceBatch.updateOne({_id,version,status,activeLeaseId})` (EvidenceBatch has `version` from `mutableOptions` and no guard); provider functions injected through config (test doubles) because tests lack mongot and must not call OpenAI. Batch end states that satisfy release gate: `available-for-human-review`+`stage:'llm'` or `failed`+`failedStage`. Moving submission `validated→pending-review` when batch becomes terminal (that is what the queue counts).
5. `ContentRevision` is immutable after submit, so passage text for embeddings comes from `readRichChapter`/`chapterTextProjection` (`rich-chapter-document.js`) for chapters; story-metadata submissions (`content.title/description/categoryIds`) have no chapter passages — the plan must say what (if anything) is embedded for story submissions (the `EmbeddingArtifact` schema and `SimilarityFinding.sourceChapterId` required field are chapter-oriented).
6. "Only NovelHub published/pending chapters, excluding the submitting author's own work": `EmbeddingArtifact` stores `authorAccountId` + `eligibilityStatus` (copied metadata, treated as non-authoritative per design doc `phase-03` row 83) → post-filter against current `Chapter`/`ContentRevision` status and `Story.authorAccountId` before the LLM (and `$vectorSearch` `filter` can pre-filter on `authorAccountId`/`eligibilityStatus` only if those fields are indexed as `filter` fields in the vector index definition).

## Open risks / unknowns

- **Freeze provenance:** `submitContent` sets `authoringFrozen=true` without writing `publicationTransition` (`author-submissions.js:369-371`), while role-removal/account-deletion write `publicationTransition.result` (`revocation.js:~116`, `admin-close-author-account.js:~70`). A later role-removal over a story already frozen-for-review overwrites `publicationTransition`, but a rejection racing *before* removal is fine; the unsafe window is rejection *after* removal — blocked in practice by submission being `cancelled`, **except** for `rejected`/other-status submissions of other chapters, and by published-revision exclusion (`revisionId ∉ published`, so approved-and-published submissions are NOT cancelled). Plan should define an explicit check (author account active + active author RoleAssignment + `publicationTransition.result` not in the two reasons).
- **`under-review` Story status is never written** though enum/guards reference it; decide whether claiming sets it (would flip `editable` checks identically to `submitted`) or leave unused.
- **`decision-pending` semantics undefined in code** (only docs): decide whether it is the moderator-claim state; claim fields have no writer, no TTL sweeper (stale `claimExpiresAt` release semantic exists only in cancel paths as `claimReleaseHistory`).
- **Evidence batch has no lease/claim version of its own** (`activeLeaseId` only; `ProcessingAttempt.leaseExpiresAt/claimVersion` are on attempts); `review-evidence.js:19` treats `activeLeaseId` truthy as "AI in progress" for the manual-defer path — clear it on every terminal/failed write.
- `AuditEvent.idempotencyScope` is not backed by a unique index; use `Notification` unique `{recipientAccountId,sourceEventKey}` and `ProcessingAttempt.attemptKey` unique for idempotency instead.
- `ModerationHistory.actorAccountId` is **required** → system/AI events cannot be written there without a system account; use `AuditEvent{actorType:'system'}`.
- Existing `reviseSubmission` for chapters 409s on `story.authoringFrozen` (`:513`) — after a story-metadata rejection that is cleared by the decision tx so OK, but a rejected story whose freeze came from role removal remains blocked (intended).
- `publicUser` roles are read per request but `requireRole` does not enforce `authorizationEpoch` for a moderator whose role was just revoked within the session's validity unless `resolveSession` already invalidated it (epoch bump on revocation); decision tx must re-check the active moderator `RoleAssignment` (as `decideApplication` does for admin).
- Mongoose `^9.11.1`, zod `^4.6.5`, Express `^5.3.0`, vitest `^5.0.3` (`package.json`): no `openai` SDK dependency (use `fetch` or add dep); OpenAI/vector index config keys are absent from `env.js`/`.env.example` (must be added as optional to avoid breaking `testConfig`).
- Line numbers marked `~` are approximate; re-read before editing. Frontend moderator pages/`SubmissionReviewPage.jsx` were only grepped for status strings, not mapped.
